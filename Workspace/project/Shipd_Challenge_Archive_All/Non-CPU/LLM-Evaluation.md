Full challenge description from page:

> Technical Standard Errata Provenance Cards
> Overview
> Technical standards are maintained through errata reports. A report usually
> quotes a compact passage, proposes a correction, and adds a short explanation.
> This benchmark asks a model to generate a small provenance card identifying the
> source standard that the report came from.
> This is an LLM Evaluation task: the model must read a terse technical repair
> note, compare it against a set of similar reference titles, and generate the
> canonical source title and year as structured JSON. The task is not to judge
> whether the correction was accepted.
> The released benchmark contains 6,754 prepared examples:
> 5,230 training rows
> 1,524 test rows
> 0 source-document overlap between train and test
> test rows come from newer source documents than the training rows
> The Task
> For each test row, generate a JSON provenance card:
> {"source_title": "...", "source_year": "..."}
> Each row contains:
> a submitted original excerpt
> a submitted proposed correction
> an optional submitter note
> sixteen similar reference titles, reference_title_01 through reference_title_16
> The correct provenance card must name the source standard title and publication
> year exactly as represented by one of the reference titles.
> The sixteen candidates for a row are the nearest neighbours of a hidden anchor
> document drawn from the true document's own neighbourhood. The set is therefore
> not built around the correct answer, and no candidate is distinguishable by
> being the one the others were selected to resemble. All sixteen are drawn from
> the same publication era as the true document, so the train/test split cannot be
> used to filter the field. Which distractors appear, where the correct candidate
> lands among them, the row identifier, and the row order in the released files
> are each drawn from independent keyed random streams. The key is not published,
> is not stored in the released package, and cannot be recovered from any released
> column. Reading the errata text is the only route to the answer.
> Dataset
> The prepared public data contains three CSV files.
> File	Description
> train.csv	Training rows with errata text, reference titles, and the target JSON provenance card.
> test.csv	Test rows with the same input columns and no target card.
> sample_submission.csv	Example submission with the required columns.
> Input columns in train.csv and test.csv:
> Column	Type	Description
> id	string	Opaque row identifier. Carries no information about the row.
> original_excerpt	string	Submitted passage from the affected standard, with direct source-number references masked.
> proposed_correction	string	Submitted proposed replacement or correction, with adjudicator notes removed.
> submitter_note	string	Submitter explanation, with adjudicator notes removed.
> reference_title_01 ... reference_title_16	string	Sixteen plausible source-standard titles with publication year, all from the same era. Distractors are drawn from the full standards index and need not themselves have errata.
> Training target column in train.csv:
> Column	Type	Description
> provenance_card	JSON string	Object with source_title and source_year for the true source standard.
> test.csv omits provenance_card.
> Evaluation
> Submissions are scored with the Provenance Card Score in [0, 1], higher is
> better.
> The grader parses each submitted provenance_card as JSON and checks two
> fields:
> source_title
> source_year
> The final score is:
> score = (
> 0.85 * exact_source_title_rate
> + 0.05 * exact_source_year_rate
> + 0.10 * confidence_calibration
> )
> Confidence calibration
> confidence is read as a probability that the full card is correct:
> p = confidence / 100. Let y be 1 when both source_title and
> source_year are correct and 0 otherwise, and let base be the mean of y
> across the submission.
> Calibration is the Brier skill score against the base-rate forecast:
> brier     = mean((p - y) ** 2)
> reference = base * (1 - base)
> confidence_calibration = clip(1 - brier / reference, 0, 1)
> If reference is zero -- every row correct, or every row wrong -- the grader
> substitutes the chance forecast's variance, (1/16) * (15/16), as the reference.
> The reference forecast is the submission's own accuracy, so a constant
> confidence scores exactly 0 no matter what constant is chosen, including a
> constant 50. Credit comes only from resolution: assigning higher probability
> to the rows that turned out to be correct than to the rows that did not. Honest,
> discriminating confidence is the scoring optimum.
> Submission Format
> Submit a CSV with exactly one row for each id in test.csv.
> Column	Type	Description
> id	string	Identifier from test.csv.
> provenance_card	JSON string	Object containing source_title and source_year.
> confidence	float	Confidence from 0 to 100 that the full card is correct.
> Example:
> id	provenance_card	confidence
> test_abc123def4567890	{"source_title":"Transmission Control Protocol","source_year":"2022"}	82.0
> test_789abc012def3456	{"source_title":"Internet Message Format","source_year":"2019"}	61.5
> Requirements:
> Include the header row.
> Include every test id exactly once.
> Do not include duplicate or extra ids.
> provenance_card must be valid JSON.
> provenance_card must contain source_title and source_year.
> confidence must be finite and in [0, 100].
> Invalid submissions raise an error during grading.
> What Not To Use
> Do not look up test rows on any live errata, standards, search, or archive site.
> Do not match test excerpts against public errata pages or cached source pages.
> Do not use hidden raw source identifiers as answer oracles.
> Do not use the private answers file or any file generated from it.
> Do not hardcode id to answer mappings.
> Do not use external LLM or hosted judge APIs at inference time.
> Allowed approaches include local fine-tuning, retrieval over the provided
> training data, traditional NLP models, and local open-weight language models.

Full challenge description from page:

> Overview: A fixed population of about eighty different language models, spanning small open-weight models through frontier-scale systems, was given the same bank of four-option multiple-choice exam items. Every model committed to exactly one option per item. Aggregating those commitments gives, for each item, the fraction of the population that landed on each of the four options.
> You are given the items and you are told which option is correct. You are never given the models' answers. Your task is to predict the population's answer distribution: for every option of every test item, what fraction of the population chose it.
> This is not an exam-answering task. The answer key is handed to you, so knowing the right answer earns nothing. What is unknown is behavioural: which items a population of language models finds hard, and when it does fail, which particular wrong option pulls the failures. Those two things vary enormously across items. On some items the population is unanimous and correct; on others the majority converges confidently on one specific incorrect option. Errors are not spread evenly over the wrong options - on items the population finds difficult, a single incorrect option typically absorbs about seventy percent of all errors, against thirty-three percent for an even spread. Finding which option that is, on an item you have never seen, from a field of study that does not appear in training, is the challenge.
> The test items come from fields of study that are entirely absent from the training data, so a solution must transfer its model of failure behaviour to unfamiliar subject matter rather than memorise field-specific difficulty.
> Practical note on what works. This challenge is compute-bound, not feature-engineering-bound. A lexical model of the item text is close to worthless here: a TF-IDF plus ridge regression over the question and option text, trained on the full training set, scores about 0.01. The intended route is to obtain publicly available pretrained language models, run them yourself over the items, and use their own answers and answer-probabilities as the basis for predicting how the larger population behaves. Calibrating on a subsample of the training items is sufficient; you do not need to run your models over all of the training data. More diverse emulator models produce better predictions than a single strong one.
> Evaluation: Metric: macro-field Brier skill score. Direction: maximize. Minimum -1.0, maximum 1.0.
> For each row you submit a share, your estimate of the fraction of the population that selected that option. Write p for your prediction, y for the observed share, and b for the published constant baseline share of that row. The baseline is 0.735860 for a row whose option is the correct one and 0.088046 for a row whose option is incorrect; these are exactly the numbers shipped in sample_submission.csv.
> Predictions are clipped into [0, 1]. A missing, blank or non-numeric share is replaced by that row's baseline value b, which contributes no skill either way. For each field f present in the hidden test set:
> skill_f = 1 - (sum over rows of f of (p - y)^2) / (sum over rows of f of (b - y)^2)
> Let raw be the mean of skill_f over the held-out fields. The reported score is raw itself when raw is at least 0, and raw / (1 - raw) when raw is negative. The second branch is a strictly increasing map from the negative half-line onto the interval (-1, 0). So a perfect submission scores 1.0, a submission carrying no item-level information scores exactly 0.0, and submissions worse than the baseline are still ranked against one another on a scale bounded below by -1.
> Why this metric: The squared error on a predicted share is the Brier score, a strictly proper scoring rule. Reporting your honest belief is optimal under it, so no score can be bought by shading predictions toward 0 or 1, and it introduces no threshold, cutoff or tuning constant whose particular value would need defending.
> Dividing by the error of the constant baseline turns that raw error into the quantity actually of interest: the share of the item-to-item variation in population behaviour that your predictions explain. This fixes both ends of the scale to something meaningful. A submission carrying no item-level information scores exactly 0.000, and reproducing the observed shares scores exactly 1.000. Because sample_submission.csv is itself the baseline, the leaderboard number reads directly as improvement over knowing nothing about the individual item. Plain mean squared error would not do this: most items are answered correctly by most of the population, so a constant guess already achieves a small absolute error and every submission would be crowded into a narrow band near the top of the range.
> The per-field scores are averaged over fields rather than pooled over rows because the held-out fields differ in size by more than a factor of ten. Pooling would let the largest few fields determine the ranking, while the property being measured is transfer to unseen fields; averaging gives every held-out field equal weight and so measures that property directly.
> The negative branch exists so that the metric never has a flat region. Simply clamping the score at 0 would make every submission at or below the baseline - random predictions, all zeros, a constant 0.25, wildly out-of-range values - score identically 0.000 and therefore be unrankable, even though those submissions are plainly of different quality. Mapping the negative half-line through raw / (1 - raw) keeps the score bounded below while preserving strict monotonicity: a submission with larger squared error always scores strictly lower than one with smaller squared error, at every level of degradation. The map is the identity on [0, 1], so nothing about the interpretation above the baseline changes.
> The metric has exactly one component on purpose. A second term rewarding identification of the most-attractive incorrect option was considered and rejected as redundant: squared error already penalises putting the error mass on the wrong option, and any such term would need an arbitrary decision threshold that the Brier score does not.
> Dataset: train.csv - one row per (item, option) pair for the training fields, 43212 rows. row_id - string - unique opaque identifier of this (item, option) pair; copy it into your submission. item_id - string - identifier of the item; the four rows of an item share it. field_id - string - opaque identifier of the field of study the item belongs to. question - string - the text of the exam item. option_text - string - the text of this particular answer option. option_index - integer - which of the item's four options this row is, from 1 to 4. is_correct_option - integer - 1 if this option is the correct answer to the item, 0 otherwise. n_models - integer - how many models in the population produced a usable answer for this item. share - float - the target. Fraction of those models that selected this option. The four shares of an item sum to 1.
> test.csv - the same columns as train.csv except share, for the held-out fields, 12412 rows.
> sample_submission.csv - a valid submission in the required format, 12412 rows. Its predictions are the constant baseline described under Evaluation, so it scores exactly 0.000.
> Submission: Submit a CSV with exactly two columns, one row for every row of test.csv. row_id - string - copied verbatim from test.csv. Treat it as opaque. share - float - your predicted fraction of the population choosing that option, in [0, 1].
> Example of the required format:
> row_id,share field_02__it_9f2c41ab7d03__o1D,0.061 field_02__it_9f2c41ab7d03__o2C,0.804 field_02__it_9f2c41ab7d03__o3D,0.052 field_02__it_9f2c41ab7d03__o4D,0.083 field_11__it_4b7e10dd92c6__o1D,0.317
> Requirements: a header row, exactly 12412 data rows, one per row_id in test.csv, and no duplicated row_id. Your predictions do not need to sum to 1 within an item, though the true shares always do.
> Rules: The only valid input signals are the item text, the option texts, the supplied correct-answer flag, and the behaviour of language models that you run yourself. The following approaches are not allowed:
> Hardcoding predictions for specific test rows or specific items.
> Retrieving published evaluation results, leaderboards, per-item scoring dumps, response logs or any other record of how existing models answered these particular items, from the internet or from any local copy. The target of this challenge is precisely such a record, and recovering it externally is not a solution.
> Using row ordering, row_id structure, item_id values or field_id values as a prediction signal instead of the content of the item. The identifiers are opaque and the option order within each item has been independently randomised, so no option position carries information.
> Using private, role-gated or API-key-based models, or calling any external inference API at prediction time.
> Using model weights or artifacts that are not publicly available and reproducible.
> The intended skill is modelling the failure behaviour of language models: predicting which items a population of models finds hard and which incorrect option attracts its errors, and transferring that to unseen fields of study. Reading the answer off a published record of these models' responses bypasses the entire problem, and exploiting identifier or ordering artifacts measures nothing about model behaviour at all.
> Pretrained model policy: Running and fine-tuning publicly available pretrained models is not merely allowed here, it is the intended route, and the challenge is designed so that compute spent running such models converts into score. There is no useful shortcut around it: a lexical model of the item text alone reaches roughly 0.01, so a solution that never runs a language model has very little to work with. Emulating the population with a single small model reaches roughly 0.29, and combining several diverse models is what pushes the score substantially higher. Fine-tuning an encoder on the training targets, calibrating raw emulator votes, and modelling the gap between your emulators and the wider population are all in scope.

Full challenge description from page:

> Response Facet Coverage Overview When a person poses an open-ended request, a strong response is expected to touch several distinct, request-specific facets at once — address a particular sub-question, get a specific fact right, take the asked-for stance, avoid a named pitfall — and different facets matter to the request to different degrees. This competition asks you to model that decomposition directly. Each item pairs a request with a single candidate response and a fixed set of eight salience-weighted facets written for that request. For every facet you output a calibrated probability that the response covers it. The submission is therefore a full coverage profile per item — eight probabilities — not a single verdict, and it is scored against a hidden per-facet coverage key. The setting is deliberately open-vocabulary and open-set: the facet sets are written freshly for each request, the requests (and their facet sets) in the test partition are disjoint from the training partition, and no facet text is shared between train and test. Whether a test facet is covered is therefore not recoverable from the training data; it is determined only by the specific candidate response and the facet text. Three properties make the data hard: facets are heterogeneous and often turn on subtle content rather than surface features; each set mixes near-universally-covered facets with contested ones where coverage is genuinely ambiguous; and the metric is a strictly proper scoring rule (a single globally-pooled salience-weighted Brier skill score), so a calibrated probability scores better than an overconfident one. Dataset Public files train.csv — one row per training item. Columns: id, request, response, facet_1…facet_8, salience_1…salience_8, cover_1…cover_8. test.csv — one row per test item. Columns: id, request, response, facet_1…facet_8, salience_1…salience_8. The cover_* columns are withheld. sample_submission.csv — a valid, correctly-formatted submission with constant placeholder predictions. Columns: id, cover_1…cover_8. Private file (organizer only) answers.csv — the hidden coverage key. Columns: id, cover_1…cover_8, identical in name and order to sample_submission.csv. Column descriptions Each row describes one request–response item together with its eight-facet set: id (string) — unique item identifier (generic token, e.g. item_9f3a1c2b). request (string) — the open-ended task or question the response is answering. response (string) — a single candidate free-form response to request, to be assessed for facet coverage. facet_1 … facet_8 (string) — the text of the eight facets the response is checked against for this request; each is a self-contained natural-language information point (e.g. "States a definite recommendation rather than listing options"). salience_1 … salience_8 (float) — how central each facet is to the request, in [0, 1]; the eight salience values of an item are non-negative and are renormalized to sum to 1 during scoring. cover_1 … cover_8 (int, target) — hidden ground-truth coverage for each facet: 1 if the candidate response covers facet_j, else 0. Present in train.csv and answers.csv; withheld from test.csv. Data example A truncated train.csv row (facets/salience abbreviated): id,request,response,facet_1,...,facet_8,salience_1,...,salience_8,cover_1,...,cover_8 item_9f3a1c2b,"Explain whether to index this column and why.","You should add a B-tree index because ...","Gives a definite yes/no recommendation",...,"Mentions write-amplification cost",0.22,...,0.05,1,...,0 Split and anti-memorization The train/test partition is built so that a model cannot win by memorization and must generalize: Disjoint requests. The split is partitioned by request: every request, together with all of its candidate responses and their facet sets, is assigned entirely to one split. No request, response, or facet set that appears in test.csv appears anywhere in train.csv. No shared items or facet text. No request, response, or facet string is shared across the two splits; facets are open-vocabulary, so the exact information points being assessed at test time were never labeled during training. Only the abstract skill transfers. What is shared across splits is the task form — read a response against a salience-weighted facet and calibrate a coverage probability — not any specific response→coverage mapping. Item order and the order of the eight facets within each item are shuffled with a data-derived seed, so neither row position nor facet position carries any signal. Submission format Submit a CSV with exactly these columns and one row per test.csv id: id,cover_1,cover_2,cover_3,cover_4,cover_5,cover_6,cover_7,cover_8 item_9f3a1c2b,0.83,0.60,0.41,0.95,0.12,0.77,0.50,0.30 Exactly one row per test item; every test id must appear exactly once. Missing ids, unknown ids, duplicate ids, or extra/unknown columns are rejected. Each cover_j is a real number in [0, 1] — the predicted probability that the candidate response covers facet_j. Values outside [0, 1], blanks, and non-numeric entries are rejected. The header row is required. The prediction width is fixed at eight columns for every row. Sample submission (constant, uninformative — every prediction is 0.5): id,cover_1,cover_2,cover_3,cover_4,cover_5,cover_6,cover_7,cover_8 item_9f3a1c2b,0.5,0.5,0.5,0.5,0.5,0.5,0.5,0.5 Evaluation The metric is Salience-Weighted Coverage Skill (SWCS), a salience-aware skill score that measures how much better a submission's coverage probabilities are than a no-information baseline. It is a single, globally-pooled salience-weighted Brier skill score, and this pooling makes it a strictly proper scoring rule: the expected-score-maximizing prediction for every facet is exactly its true coverage probability, so calibrated probabilities are rewarded and confident errors are penalized more than hedged ones. Higher is better. For each item with predictions p[1..8] ∈ [0,1], ground truth t[1..8] ∈ {0,1}, and non-negative salience weights w[1..8], compute a per-item salience-weighted Brier term and a base-rate reference term: RHO = mean of all cover_j over the whole scored set # global coverage base rate EPS = 1e-6 def item_terms(p, t, w): w = w / sum(w) # renormalize salience to sum to 1 brier = sum(w[j] * (p[j] - t[j])**2 for j in 1..8) # salience-weighted Brier of predictions ref = sum(w[j] * (RHO - t[j])**2 for j in 1..8) # salience-weighted Brier of the base-rate baseline return brier, ref The brier and ref terms are summed over the entire scored set and the skill is normalized exactly once — never per item, and never per truth-defined group: total_brier = sum of item brier over ALL scored items total_ref = sum of item ref over ALL scored items score = 1 - total_brier / max(total_ref, EPS) # 0 if no better than base rate, 1 if perfect score = max(0.02, score) # small positive floor; the raw metric is otherwise unbounded below Because the denominator total_ref is summed over the whole set, it depends only on the realized labels and the fixed salience weights — it is a constant with respect to the predictions. Minimizing the pooled Brier therefore drives each facet's prediction to its true coverage probability regardless of its salience, which is precisely the strict-propriety guarantee. (Two constructions are deliberately avoided because they would break it: dividing each item's Brier by its own ground-truth-dependent reference, and macro-averaging a per-stratum skill whose stratum is defined by the realized coverage vector — both introduce an outcome-dependent weighting that can reward systematic overconfidence.) For transparency, per-coverage-band skills over the same pooled formula are reported as diagnostics — sparse (fewer than 3 of 8 facets covered), partial (3 to 5), and dense (6 or more) — but they are not part of the headline score, which is the single global pool above. The training and test collections are balanced across these bands so all coverage regimes are represented. Score components. The headline is one salience-weighted Brier skill score, globally pooled, whose reference baseline is predicting the base rate RHO for every facet; there is no macro-average and no per-item or per-group normalization; the 0.02 floor is a platform requirement, not part of the metric definition. The reported per-band skills are diagnostics only. Baselines. A constant submission that predicts the base rate RHO for every facet scores 0.0 skill (floored to 0.02) — this is the chance baseline; the constant placeholder 0.5 scores essentially the same. A submission drawn uniformly at random scores below zero on average. A perfect submission scores 1.0. Range. The score is bounded above by 1.0 and is unbounded below (a confidently-wrong submission is strongly negative). Higher is better; the grade direction is maximize. What Not To Use (Prohibited Methods) This challenge is about learning to judge coverage against unseen facets. The following are prohibited: No external coverage keys. Do not use any external pre-computed facet judgments, rubric/checklist annotations, coverage labels, reward-model scores, or human/LLM preference annotations for the same requests or responses to recover the hidden cover_* values. No source matching. Do not attempt to match requests, responses, or facet strings back to any public corpus, benchmark, or model-feedback dataset to look up or reconstruct coverage labels. No id-based hardcoding. Do not hardcode id→coverage mappings, memorized lookups, or any per-item constants; the test ids are opaque tokens and must be scored only from request, response, and the item's facet set. No train/test leakage or private-label tuning. Do not train on, or tune hyperparameters against, the private coverage key, and do not use test-set facet statistics to back out labels. Do not manually estimate coverage for test items by hand. Model your own judge. Predictions must come from a model or method that reads each candidate response against each facet. Purely structural shortcuts that ignore the response text — scoring by response length, facet salience, facet position, or per-column frequency — are against the spirit of the task; the metric's base-rate reference makes any response-independent or constant prediction score at the chance baseline. &nbsp;

Full challenge description from page:

> Overview: Each case is one language model paired with one benchmark subtask. You are told almost nothing about the model: only how it answered every item in that subtask under four prompt templates. Four. From that, you must rank all of the subtask's items from most to least fragile, where fragile means the model's answer flips between correct and incorrect as the wording of the prompt changes across the remaining one hundred and thirty to two hundred and sixty templates you never get to see. You are not working blind. For every subtask you are given the complete correctness matrices of the other models, across every template, and the full text of every prompt template including the four you were shown and the ones you were not. What you are missing is the one thing that matters most: how this particular model behaves beyond those four observations. The difficulty is that four templates is far too few to measure fragility directly. Computing fragility from the four you were given scores 0.407. Ignoring the model entirely and copying the average fragility of the other models scores 0.222. Blending the two naively scores 0.471. Observing eleven templates instead of four would score 0.661, and fifty-seven would score 0.895 - so the information is there, and the gap between 0.471 and what the data can support is the room this challenge lives in. Evaluation: The metric is the mean Spearman rank correlation, written mean_spearman. For one case, your submitted order of the item ids is compared against the true order of those items by instability. Spearman's rank correlation between the two orderings is computed, and the score for the challenge is the mean of that value over every case in the evaluation set. It ranges from -1 to Higher is better. A submission that lists only some of the items has the remainder placed after the ones it listed, sharing the average of the leftover positions, so a partial list is scored rather than rejected. Why this metric: the deliverable is an ordering of every item in a subtask, and what a user of this prediction wants is the whole ordering, not just its head. A practitioner deciding which questions of their evaluation set need to be checked under several phrasings cares about the ranking throughout, because the cut-off they apply depends on their budget, not on ours. Spearman measures exactly that ordering agreement, is invariant to any monotone rescaling of whatever score you rank by, and needs no threshold. That invariance matters: it means there is no calibration axis to tune, and two submissions that induce the same order always receive the same score. No second component is combined with it. A top-k metric such as NDCG or precision at k would answer a narrower question than the ordering the task actually asks for, and it would need a k that nothing in the data justifies; item counts differ between subtasks, so any fixed k would weigh subtasks unequally. A per-benchmark macro average would also be redundant, because the evaluation set is already balanced by construction at sixty cases from each family, so the plain mean over cases weighs the two families equally without being told to. Floor and ceiling, all measured on the evaluation cases. A perfect submission scores 1.0. Ranking items at random scores -0.004, and the supplied sample_submission, which simply lists items in their natural order, scores 0.066. Copying the mean instability of the reference models scores 0.222. Computing instability directly from the four calibration templates scores 0.407, and a naive blend of those two signals scores 0.471, which is the strongest simple baseline and the number to beat. The ceiling is not 1.0 in practice: instability itself is estimated from a finite number of templates, and observing eleven of the held-out templates would score 0.661 while observing fifty-seven would score 0.895. Those two figures bracket what additional evidence is worth, and the distance from 0.471 up towards them is the achievable headroom. The min and max in config.yaml are the metric's own bounds of -1 and 1.
